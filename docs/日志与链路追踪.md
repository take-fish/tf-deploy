# 日志与链路追踪

FishMatrix 的统一异常处理体系以**链路编号**为线索：网关为每个请求分配编号，Java 服务沿用该编号写结构化日志并随响应返回；出问题时复制编号，就能在流水线中台里看到这条请求前后的完整日志。

## 一、整体链路

```text
浏览器 / 调用方
      │  Authorization、业务请求
      ▼
tf-gateway（Go）
      │  生成 trace_id（32 位十六进制）
      │  traceparent: 00-<trace_id>-<span_id>-01
      │  X-Request-ID / X-Trace-ID: <trace_id>
      ▼
tf-user / tf-chat / tf-reader / tf-game / tf-music（Spring Boot）
      │  Micrometer Tracing 提取 traceparent，写入 MDC(trace_id / span_id / request_id)
      │  LogstashEncoder 输出一行一个 JSON 到 stdout
      │  错误响应体携带 traceId / requestId / path / timestamp
      │  响应头回写 X-Trace-ID / X-Request-ID
      ▼
Docker stdout ──► Alloy（容器发现 + 打 stack/container/compose_service 标签）
      │
      ▼
Loki（单实例，保留 14 天）
      │
      ├──► tf-console 日志检索页 `/logs`（推荐给开发和运维）
      ├──► Grafana Explore（http://127.0.0.1:13000）
      └──► scripts/trace.sh（命令行）
```

要点：

- 网关**不信任**外部传入的 `X-Request-ID` / `traceparent`，一律重新生成并覆盖，防止伪造和编号冲突。
- 服务间调用（如 tf-chat → tf-user）通过 `RestClientTraceInterceptor` 继续传递 `traceparent`，全链路共用一个编号。
- WebSocket 每帧日志也会带上建立连接时的编号（通过 `Traces` 工具写入 MDC）。
- 异步线程、线程池任务使用 `Traces.wrap(...)` 传递上下文，避免日志丢编号。

## 二、编号与请求头

| 名称 | 位置 | 格式 | 说明 |
|---|---|---|---|
| `trace_id` | 日志 `trace_id`、响应头 `X-Trace-ID`、错误体 `traceId` | 32 位小写十六进制 | 主键，前端展示为“编号” |
| `request_id` | 日志 `request_id`、响应头 `X-Request-ID`、错误体 `requestId` | 8~64 位十六进制 | 默认等于 trace_id；兼容旧日志 |
| `span_id` | 日志 `span_id` | 16 位十六进制 | 单个 Span 标识，用于区分同一次请求内的不同阶段 |
| `traceparent` | 请求头 | W3C `00-<trace_id>-<span_id>-01` | 服务间传播的标准格式 |

前端在错误提示中展示“编号 xxxx”，也可以从响应头 `X-Trace-ID` 读取。检索时支持直接粘贴整段错误提示，中台会自动提取其中的十六进制编号。

## 三、日志格式

Java 服务输出单行 JSON（Logstash 格式），主要字段：

| 字段 | 说明 |
|---|---|
| `@timestamp` | 带时区的时间（Asia/Shanghai） |
| `message` / `msg` | 日志正文 |
| `level` | `INFO` / `WARN` / `ERROR` 等 |
| `logger` | 日志来源类名 |
| `thread` | 线程名 |
| `service` | 服务名（`spring.application.name`，如 `tf-user`） |
| `env` | `production` / `test` |
| `version` | 镜像版本号 |
| `trace_id` / `span_id` / `request_id` | 链路字段，仅在请求上下文内存在 |
| `stack_trace` | 异常栈（有异常时） |

访问日志由 `TraceContextFilter` 统一输出，`event=http.access`，包含 `http_method`、`http_path`、`http_status`、`duration_ms`。不会记录查询串，避免 WebSocket ticket 等敏感参数进日志。

网关使用 Go `slog` JSON 输出，字段为 `time`、`level`、`msg`、`service`、`env`、`trace_id` 等。

Loki 中所有日志都带流标签：

| 标签 | 示例 | 来源 |
|---|---|---|
| `stack` | `fishmatrix` | Alloy 固定写入 |
| `container` | `fm-user`、`fm-test-user` | Docker 容器名 |
| `compose_service` | `user`、`gateway` | compose 服务名 |
| `service_name` | `fm-user` | Docker 服务名 |
| `stream` | `stdout` / `stderr` | 容器输出流 |

> `env`、`service`、`trace_id` 等是 **JSON 字段**，不是 Loki 流标签。检索接口会根据 Loki `/labels` 动态确认真实标签，避免把解析字段拼进流选择器。

## 四、流水线中台检索

### 入口

流水线中台顶部导航 → **日志检索**（`http://<集中机>:8301/logs`）。

页面参数：

- **编号**：必填，8~64 位十六进制；可粘贴整段错误提示自动提取。
- **环境**：全部 / 生产 / 测试，默认全部。
- **上下文**：命中行前后各 30 / 50 / 100 行，默认 30。
- **时间范围**：1h / 6h / 24h / 7d / 14d，默认 24h。

结果按时间升序排列，命中行前面有 `*` 标记并高亮；同一次请求分散在多个容器（如网关 + 用户服务）时，会按来源分别取上下文后合并。

### 鉴权

中台日志接口使用 `X-Log-Token` 头校验：

1. 首次部署执行 `bash scripts/ensure-observability-secrets.sh`，脚本会幂等生成 `TF_CONSOLE_LOG_TOKEN`（不打印值）。
2. 页面在检测到“需要口令”时提示输入，口令保存在当前浏览器会话的 `sessionStorage`，关闭标签页即失效。
3. 中台环境变量 `TF_CONSOLE_LOG_TOKEN` 为空时，接口不启用手令校验（仅建议本地开发使用）。

### 接口

| 方法/路径 | 说明 |
|---|---|
| `GET /api/v1/logs/meta` | 返回是否启用手令、Loki 是否可用、保留天数、上下文与范围选项 |
| `GET /api/v1/logs/search` | 按编号检索日志与上下文 |

`/api/v1/logs/search` 参数：

| 参数 | 取值 | 默认 |
|---|---|---|
| `id` | 8~64 位十六进制（大小写均可） | 必填 |
| `env` | `all` / `prod` / `test` | `all` |
| `lines` | `30` / `50` / `100` | `30` |
| `range` | `1h` / `6h` / `24h` / `7d` / `14d` | `24h` |

响应字段：

```json
{
  "id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "env": "prod",
  "contextLines": 30,
  "range": "24h",
  "start": "2026-10-21T06:00:00Z",
  "end": "2026-10-22T06:00:00Z",
  "matched": 3,
  "streams": 2,
  "truncated": false,
  "warnings": [],
  "entries": [
    {
      "timestamp": "2026-10-22T15:13:21.128+08:00",
      "timestampNs": "1792653201128512700",
      "level": "warn",
      "service": "tf-user",
      "env": "production",
      "logger": "synthetic",
      "message": "登录失败：密码错误",
      "line": "{...原始 JSON...}",
      "matched": true
    }
  ]
}
```

限制与上限：

- 命中最多 200 行；同一查询最多取 10 个来源的上下文；最终最多 3000 行。
- 单行超过 6000 字符会截断；`truncated=true` 表示触达上限。
- 先查 `trace_id`，无结果时自动回退查 `request_id`。
- 单次请求总超时 15 秒。

## 五、命令行 `trace.sh`

```bash
cd tf-deploy

# 默认读 .env 里的 CONSOLE_URL / TF_CONSOLE_LOG_TOKEN
bash scripts/trace.sh 4bf92f3577b34da6a3ce929d0e0e4736

# 直接粘贴前端错误提示
bash scripts/trace.sh "发送失败（编号 4bf92f3577b34da6a3ce929d0e0e4736）" --env prod

# 查看更大上下文与更长时间范围
bash scripts/trace.sh 4bf92f... --env all --lines 100 --range 7d

# 输出原始 JSON 或接口原始响应
bash scripts/trace.sh 4bf92f... --raw
bash scripts/trace.sh 4bf92f... --json

# 覆盖中台地址 / Python 解释器
CONSOLE_URL=http://127.0.0.1:18301 PYTHON_BIN=python bash scripts/trace.sh 4bf92f...
```

输出中带 `*` 的是命中行。退出码：0 有结果，1 无结果或查询失败。

## 六、Loki / Alloy / Grafana 运维

| 组件 | 镜像 | 访问 | 数据卷 |
|---|---|---|---|
| `fm-loki` | `grafana/loki:3.5.1` | `127.0.0.1:13100`（宿主机回环） | `fishmatrix_loki-data` |
| `fm-alloy` | `grafana/alloy:v1.8.3` | 无 | `fishmatrix_alloy-data` |
| `fm-grafana` | `grafana/grafana:12.1.0` | `127.0.0.1:13000`（宿主机回环） | `fishmatrix_grafana-data` |

- 三者都在 `docker-compose.middleware.yml` 中，与共享中间件同一 compose 项目。
- Alloy 只采集容器名匹配 `fm-*` 的 Docker stdout，并排除日志组件自身。
- Loki 使用 filesystem + TSDB（schema v13），保留 336 小时（14 天），超期由 compactor 清理。
- Grafana 已预置 Loki 数据源；管理员账号见 `.env` 中 `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD`。
- Grafana 与 Loki 默认只绑定回环地址，不对外网开放；如需远程访问，请通过 SSH 隧道，不要直接改绑 `0.0.0.0`。

常用命令：

```bash
docker compose -f docker-compose.middleware.yml up -d loki alloy grafana
docker compose -f docker-compose.middleware.yml logs -f alloy
docker compose -f docker-compose.middleware.yml restart alloy
curl -s http://127.0.0.1:13100/ready          # Loki 就绪检查
curl -s http://127.0.0.1:13100/loki/api/v1/labels
```

手工查询（Grafana Explore 或 curl）：

```logql
# 按编号精确检索
{stack="fishmatrix"} | json | trace_id="4bf92f3577b34da6a3ce929d0e0e4736"

# 再叠加错误级别
{stack="fishmatrix"} | json | trace_id="4bf92f..." | level=~"WARN|ERROR"

# 只看某个服务
{stack="fishmatrix", compose_service="user"} | json | trace_id="4bf92f..."
```

> 在 Loki 查询里，`env=`、`service=` 可以作为 `| json` 之后的过滤条件，但它们不能出现在 `{}` 流选择器内。

## 七、排查步骤

1. **拿到编号**：前端错误提示中的“编号”，或响应头 `X-Trace-ID`。
2. **中台检索**：进入 `/logs`，填编号，先选 24h 与“全部”，看命中数量与分布。
3. **缩小范围**：命中太多时切到对应环境；命中太少时扩大到 7d / 14d。
4. **看上下文**：重点看命中行前后 30 行，定位请求开始、依赖调用、异常栈与响应状态。
5. **跨服务串联**：同一编号会同时出现在网关与服务日志中，可通过 `service` 字段区分。
6. **命令行**：在集中机上直接 `bash scripts/trace.sh <编号>`，便于复制给同事。
7. **Grafana**：需要复杂筛选、统计或将结果共享给他人时，用 Explore 打开同一条 LogQL。

常见现象：

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示“编号必须是 8-64 位十六进制” | 粘贴内容里没有编号，或编号被截断 | 重新复制完整错误提示 |
| 只有命中行没有上下文 | 该编号前后的日志不在 Loki 保留期或时间范围内 | 扩大时间范围；确认服务日志已切到 JSON 格式 |
| 查不到 2026-10-22 之前的老日志 | 日志体系上线前的旧容器输出为明文，且没有 trace_id | 旧日志只能按内容搜索，不再支持按编号检索 |
| 页面提示需要口令 | 中台配置了 `TF_CONSOLE_LOG_TOKEN` | 向运维索取口令，或查看 `.env` |
| `warnings` 提示部分上下文获取失败 | Loki 或网络瞬时异常 | 稍后重试；必要时 `docker compose ... logs loki` |
| 结果很多且 `truncated=true` | 达到 200 命中 / 3000 行上限 | 缩小时间范围或环境后重试 |

## 八、上线切换注意

- 生产/测试 Java 服务与网关必须升级到包含统一日志与链路的新镜像，才会输出 `trace_id` 与 JSON 日志。
- 网关的 `env` 来自 `APP_ENV`，默认 `production`。测试编排 `docker-compose.test.yml` 已显式设置 `APP_ENV=test`；新增环境时必须同样设置，否则测试日志会被归到生产并在按环境筛选时串环境。
- 新镜像启动后，旧容器的明文日志仍会留在 Loki 中直到过期，按编号检索时自然查不到。
- `TF_CONSOLE_LOG_TOKEN` 与 Grafana 管理员密码由 `scripts/ensure-observability-secrets.sh` 生成，请勿提交到仓库或粘贴到公开渠道。
