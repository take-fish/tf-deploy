### 3.1 Lombok 统一

六个 Java 仓统一用 Lombok 消除手写构造器与 Logger，只引入 `@RequiredArgsConstructor` 与 `@Slf4j`，不引入 `@Data` / `@Getter` / `@Setter`（避免无意暴露可变状态）。

| 仓库 | `@RequiredArgsConstructor` | `@Slf4j` |
|---|---:|---:|
| tf-common | 5 | 3 |
| tf-user | 9 | 3 |
| tf-chat | 14 | 7 |
| tf-reader | 14 | 2 |
| tf-game | 39 | 11 |
| tf-music | 9 | 0 |

跳过构造器改造的情况：构造参数带 `@Value` 注入、存在多个构造器、构造体内含非赋值语句、字段声明顺序与构造参数顺序不一致。自定义 Logger 名（`com.fishmatrix.http.AccessLog`）保留手写，不用 `@Slf4j` 替换。

### 3.2 store 持久化边界（批次 2）

审计口径：`store` / `repository` 包只做参数化 SQL、行映射与事务内幂等写入；积分、时限、权限、状态流转等判断一律放 Service。

| 仓库 | 位置 | 处理 |
|---|---|---|
| tf-game | `store/PlayerStatRepository` | 抽出 `PlayerStatRules`（冠军 30 / 亚军 10 / 胜 3 / 负 1 / 冠军奖励 10），仓储改为 `addTitle` / `addMatch` / `addGameMatch` 增量写入，分数由 Service 传入；`recordBreakoutScore` 改为纯 SQL `raiseBestScore`（`GREATEST` 原子取高） |
| tf-chat | `repository/ChatMessageRepository` | 删除 `recall` 中的归属、群聊、时限判断；拆成 `findById` + `markRecalled`（仅写 `recalled_at IS NULL` 条件），规则回到 `ChatService.recall` |
| 其余 | `TournamentRepository`、`ExerciseRepository`、`MatchRepository`、`NotificationRepository`、`BlindXiangqiRepository`、music / user 各仓储 | 复核为纯持久化：仅空值/游标/动态条件拼接与 upsert 兜底，无业务判断，不改 |

评审结论：仓储写参数化 SQL 属于持久层职责，方案未要求引入 ORM；`tf-reader` 已用 MyBatis-Plus，其 `mapper` 包同属持久层，保留。`service/SmokeService` 407 行属服务编排，低于 600 行门禁，不拆。

### 8.5 结论

- **#150 慢接口优化：不执行代码改动。** 无接口 p95 超过 30ms，8 并发下无劣化；`game/tournaments` 25.8KB 为最大载荷，但单页仅请求一次且 16ms 内返回，拆分响应收益小于兼容成本。后续阈值：任一列表接口 p95 > 100ms 或载荷 > 100KB 再优化。
- **#152 虚拟滚动：不引入。** 最大列表为阅读页 380 个章节按钮（1554 节点），页面首屏与其它页面持平；赛事/用户/音乐列表均 ≤ 20 行。引入虚拟滚动的收益不足，反而增加章节定位、键盘导航与滚动同步的复杂度。后续阈值：单列表 > 1000 行或页面 DOM > 5000 节点再评估。
- 聊天突发全部命中限流属既定策略，不是背压丢失；背压与重连加固在 #151 单独处理。

### 8.6 WS 背压与重连加固（#151）

`tf-web` 的 `chatSocket.ts` / `gameSocket.ts` 同步改造：

| 项 | 聊天通道 | 游戏通道 |
|---|---|---|
| 出站背压上限 | 1MB（用户消息被拒时提示「网络拥塞，消息未发送，请稍后重试」`WS_BACKPRESSURE`） | 512KB（动作帧静默拒绝，调用方沿用「未发送」提示） |
| 浏览器 `offline` | 主动置空 socket、停心跳、立即上报 `reconnecting`，15 秒兜底重试 | 同左 |
| 浏览器 `online` | 清退避计时器并立刻重连 | 同左 |
| 稳定连接阈值 | 连上 10 秒后才清零退避计数，避免「连上即被踢」时按 1 秒风暴重试 | 同左 |
| 旧 socket 守卫 | `onclose` 里比对 `this.ws !== ws` 直接返回，避免多开连接 | 同左 |

排查记录：CDP `Network.emulateNetworkConditions {offline:true}` 与真实断网一样，关闭握手发不出去，`onclose` 迟迟不触发，徽标一直停在在线。因此不能只靠 `onclose`，必须在 `offline` 事件里主动进入重连态。

验证（`D:\develop\ws-reconnect-e2e.mjs`，Edge headless + CDP，测试栈 `localhost:18088`）：

| 用例 | 结果 |
|---|---|
| 聊天初始在线 | PASS（134ms） |
| 断网后进入重连态 | PASS（浏览器事件触发，非手动派发） |
| 恢复网络后重新在线 | PASS（浏览器事件触发） |
| 调度通道初始在线 | PASS |
| 断网后调度通道进入离线/重连态 | PASS（浏览器事件触发） |
| 恢复网络后调度通道重新在线 | PASS（浏览器事件触发） |

前端门禁：type-check / oxlint / eslint / build 全过，单测 201 个（33 个测试文件），其中新增 11 个 WS 用例（聊天通道 5 个；游戏通道新建 `gameSocket.spec.ts` 6 个：重连后重新关注、背压拒绝、旧 socket 守卫、退避递增与稳定清零、浏览器断网/恢复、ticket 401 停止重连）。
