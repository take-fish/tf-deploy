# 消息队列（RocketMQ）

FishMatrix 使用 RocketMQ 5.3 做服务间领域事件发布。基础设施与发布器已就绪，
并已接入第一组**旁路业务事件**（tf-reader 访问申请）；消费者、重试/死信治理尚未接入。

## 架构

- 生产与测试**共用一个 broker**，通过 topic 前缀与 producer group 前缀隔离：

| 项 | 生产 | 测试 |
|---|---|---|
| topic 前缀 | `FM_` | `FM_TEST_` |
| producer group | `fm-<service>` | `fm-test-<service>` |
| 诊断 topic | `FM_SYSTEM_PROBE` | `FM_TEST_SYSTEM_PROBE` |

- 集群名 `fishmatrix`，broker 名 `fm-broker`，线程模型为单机 `ASYNC_MASTER`。
- 容器 `fm-rocketmq-nameserver` / `fm-rocketmq-broker` 由 `docker-compose.middleware.yml` 定义，
  只接入 `fishmatrix-mw` 网络，**不映射宿主机端口**（管理命令通过 `docker exec` 执行）。
- 资源限制：nameserver 448m、broker 1536m；JVM 堆通过 `JAVA_OPT_EXT` 显式设置
  （nameserver `-Xmx256m`、broker `-Xmx768m`），避免默认 8g 堆挤占同机的 MySQL/Redis/Nacos。
- 上限按实测稳态上调：堆之外还有 metaspace、线程栈与 direct buffer，早期 320m/1g 的上限下
  实测占用达到 278m/842m（87%/82%），broker 峰值曾触及 1g；放宽后稳定在 50%/65%。
  调整 `deploy.resources.limits.memory` 时务必保留至少 30% 余量，否则容器会被 OOM kill。
- 数据卷：`fishmatrix_rocketmq-store`（仅 broker）。
  - 命名卷首次创建时属主是 `root:root`，而镜像内 broker 以 UID 3000（`rocketmq`）运行，
    直接挂载会因 `/home/rocketmq/store/lock` 无写权限而反复重启。
  - compose 里的 `rocketmq-init`（`alpine`，`chown 3000:3000 /store`）在 broker 之前执行一次，
    broker 通过 `depends_on.condition: service_completed_successfully` 等待它完成。
  - 手工重建卷时同样需要先改属主，否则 broker 会 `Restarting (255)`。
- broker 关闭了自动创建 topic / 订阅组，所有 topic 由脚本预建。

## 部署

在 `tf-deploy` 目录：

```bash
docker compose -f docker-compose.middleware.yml up -d rocketmq-nameserver rocketmq-broker
docker compose -f docker-compose.middleware.yml ps
bash scripts/init-rocketmq.sh test
```

- `init-rocketmq.sh` 幂等创建 `TOPICS` 数组里的全部 topic（诊断探针 + 已接入的业务事件），
  `prod` 参数创建生产前缀的同名 topic。
- 新增业务事件 topic 时，在脚本 `TOPICS` 中登记并重跑。
- 生产 topic 只在生产启用时创建：`bash scripts/init-rocketmq.sh prod`。

## 管理命令

镜像里 `mqadmin` 不在默认 `PATH`，需要先切到其 `bin` 目录再用 `sh` 启动。
Git Bash 会改写以 `/` 开头的参数，所以宿主机侧要加 `MSYS_NO_PATHCONV=1`：

```bash
MSYS_NO_PATHCONV=1 docker exec -w /home/rocketmq/rocketmq-5.3.3/bin fm-rocketmq-broker sh mqadmin clusterList -n rocketmq-nameserver:9876
MSYS_NO_PATHCONV=1 docker exec -w /home/rocketmq/rocketmq-5.3.3/bin fm-rocketmq-broker sh mqadmin topicList -n rocketmq-nameserver:9876 -c fishmatrix
MSYS_NO_PATHCONV=1 docker exec -w /home/rocketmq/rocketmq-5.3.3/bin fm-rocketmq-broker sh mqadmin queryMsgByKey -n rocketmq-nameserver:9876 -t FM_TEST_SYSTEM_PROBE -k <eventId>
```

在 Linux 宿主机或 `init-rocketmq.sh` 之类的脚本内执行时不需要 `MSYS_NO_PATHCONV=1`。

## 配置

所有 MQ 配置都在 Nacos `tf-<service>.yaml`（group `FM`，生产/测试按 namespace 隔离），
不使用 compose 环境变量：

```yaml
fm:
  messaging:
    enabled: false
    log-events: false
    name-server: rocketmq-nameserver:9876
    topic-prefix: FM_TEST_
    producer-group: fm-test-game
    send-timeout-ms: 3000
    diagnostics-on-startup: false
```

- 只有 `tf-common >= 1.2.0` 的服务识别这些属性；未升级的服务读到也不连接。
- `enabled=true` 时 `name-server` 必填，服务启动即创建生产者；broker 不可达会导致启动失败。
- 测试环境中 `tf-game` 打开 `enabled` 与 `diagnostics-on-startup`（连通性探针）；
  `tf-reader` 打开 `enabled` 与 `log-events`（访问申请事件）。其余服务保持关闭。
- 生产模板全部关闭；生产启用需单独授权。
- 修改模板后重发对应环境配置：测试 `bash scripts/init-test-nacos.sh`，生产 `bash scripts/init-nacos.sh`。

## 发送语义

- 同步发送，超时 `fm.messaging.send-timeout-ms`（默认 3000ms）。
- topic = `topic-prefix + type`，tag = `type`，keys = 事件 `key`（空则 eventId）。
- 消息体为 `DomainEvent` JSON：`eventId/type/source/occurredAt/traceId/key/payload`。
- 失败抛 `EventPublishException` 并记录 ERROR，不隐式重试；补偿由业务调用方负责。
- `type` 只允许 `[A-Za-z0-9_-]`，约定大写 + 下划线。

## 已接入的业务事件

| 服务 | type | key | payload | 触发点 |
|---|---|---|---|---|
| tf-reader | `READER_ACCESS_REQUESTED` | 申请 ID | requestId / bookId / ownerId / requesterId / status=PENDING | 私有书籍访问申请创建或重新提交 |
| tf-reader | `READER_ACCESS_DECIDED` | 申请 ID | requestId / bookId / requesterId / actorId / status | 通过 / 拒绝 / 撤销 / 取消，`status` 为 `APPROVED` / `REJECTED` / `REVOKED` / `CANCELLED` |

- 访问申请属于旁路业务：事件只用于后续通知、审计与统计，**发布失败只记 WARN，不影响申请与审批结果**。
- 有事务时注册 `afterCommit` 再发送，事务回滚不会对外发出事件。
- 新事件 topic 必须先登记到 `init-rocketmq.sh` 并重跑，否则 broker 返回 `No route info of this topic`。

## 测试栈验收

1. `docker compose -f docker-compose.middleware.yml ps`：nameserver/broker 为 healthy。
2. `bash scripts/init-rocketmq.sh test`：topic 列表包含 `FM_TEST_SYSTEM_PROBE`、`FM_TEST_READER_ACCESS_REQUESTED`、`FM_TEST_READER_ACCESS_DECIDED`。
3. `bash scripts/init-test-nacos.sh` 发布测试配置。
4. `bash scripts/build-test-local.sh game` 构建 tf-game 1.2.0 镜像。
5. `docker compose -f docker-compose.test.yml up -d --no-deps --force-recreate game`。
6. `docker logs fm-test-game 2>&1 | grep 'MQ 启动探针'` 能看到 `SYSTEM_PROBE` 与 eventId。
7. 用 `queryMsgByKey` 按该 eventId 查到消息。
8. 游戏 REST/UI 冒烟无回归；未启用的服务（user/chat/music）日志无 RocketMQ 连接。
9. `bash scripts/build-test-local.sh reader` 重建 tf-reader 并重启，日志出现生产者启动、无 `No route info of this topic`。
10. 走一次访问申请（发起 + 审批），用 `queryMsgByKey` 按申请 ID 分别查 `FM_TEST_READER_ACCESS_REQUESTED` / `FM_TEST_READER_ACCESS_DECIDED` 能查到消息；申请与审批接口正常返回。

> 测试环境 `fm-test` 命名空间里可能注册了多个 `tf-reader` 实例（例如分机 `10.28.15.57:18103`
> 与本机 `172.21.0.4:8103` 同时在线）。网关会在实例间轮询，落到未升级实例的请求不会发出事件。
> 验证单个实例时用 `READER_BASE=http://<host>:<port> node reader-mq-e2e.mjs` 直连，
> 或先确认所有实例都已升级到同一镜像。

## 生产启用清单（需单独授权）

1. 确认 `deploy/nacos/prod/tf-<service>.yaml` 的 `fm.messaging.enabled` 改为 `true`。
2. 确认 `fm-rocketmq-broker` 运行正常，并执行 `bash scripts/init-rocketmq.sh prod`。
3. 发布生产 Nacos 配置（`bash scripts/init-nacos.sh`）。
   - 只改了一个服务时，建议只发布该 dataId，避免整体重发把线上的临时调整覆盖回模板。
4. 发布使用 `tf-common >= 1.2.0` 的对应服务版本。
5. 重启服务，检查启动日志与探针消息。
6. 回滚：`enabled` 改回 `false`，重发 Nacos 并重启服务；broker 可保留。

## 故障排查

| 现象 | 排查 |
|---|---|
| `No route info of this topic` | topic 未预建或 broker 未注册，运行 `init-rocketmq.sh` 并检查 `clusterList` |
| 服务启动失败：name-server 未配置 | Nacos 模板 `fm.messaging.name-server` 为空 |
| 服务启动失败：生产者启动失败 | broker 未就绪、网络不通或 nameserver 地址错误 |
| broker `Restarting (255)`，日志含 `FileNotFoundException: .../store/lock (Permission denied)` | 数据卷属主不是 UID 3000；运行 `docker compose -f docker-compose.middleware.yml up -d rocketmq-init`，或 `MSYS_NO_PATHCONV=1 docker run --rm -u root -v fishmatrix_rocketmq-store:/store alpine chown -R 3000:3000 /store` |
| 镜像拉取失败 | 当前环境访问 Docker Hub 受限时回退 `apache/rocketmq:5.3.2`（与客户端 5.3.3 兼容） |
| 内存占用过高 | 检查 `JAVA_OPT_EXT` 与 compose `deploy.resources.limits.memory` 是否生效 |
| 无法从宿主机直连 9876/10911 | 设计如此，管理操作通过 `docker exec` |
